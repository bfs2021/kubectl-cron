# kubectl-cron v0.1

Status: confirmed design for the v0.1 implementation.

## Purpose and delivery boundary

Provide read-only inspection of CronJob scheduling information and offline Schedule Explanations through `kubectl cron`.

The first implementation includes the command and release skeleton, offline `explain`, the CronJob-only Overview, a factual Summary, configuration/calculation Findings, and versioned JSON/YAML Reports. Rich single-object Inspection, retained run history, logs, diagnose, calendar, timeline, watch, and all cluster mutations are outside this release.

Use the module `github.com/mertdotcc/kubectl-cron`, an Apache 2.0 license, and the established kubectl-probes presentation and release conventions. Keep the demo environment under `hack/demo-cluster/` in this repository.

## Inputs and selection

- Live selection reads only `batch/v1` CronJobs. Honor standard kubeconfig, context, namespace, all-namespaces, and connection flags.
- `-l/--selector` selects CronJob labels. It does not select Job or Pod labels.
- `[NAME]` selects one CronJob for the same Overview. Also accept `cronjob/NAME` to address names that collide with subcommands.
- `-f/--filename` is repeatable and accepts local YAML/JSON definitions, multiple documents, Lists, and stdin. File-backed Overview and Explanation remain entirely offline.
- A bare expression and file input cannot be combined. `--tz` belongs to bare-expression Explanation; object-based input uses the object's timezone or an explicit assumption.
- Preserve file-declared namespaces. Missing file metadata is not evidence of a live namespace or cluster state.
- Reject malformed inputs and unsupported resource kinds with an actionable operational error.

## Schedule calculations

Use the controller's robfig/cron parser semantics, including supported descriptors, day-of-month/day-of-week behavior, and DST behavior. Guard malformed input consistently with the pinned controller parser. Pure calculation code receives an explicit evaluation time.

NEXT is the first nominal Occurrence strictly after the evaluation time under the current Schedule. It does not promise Job creation or predict overdue controller catch-up. Suspended objects display SUSPENDED instead of a forthcoming execution claim.

Calendar schedules use their effective timezone. Relative schedules require an explicit, reported reference point; object calculations use available scheduling timestamps, while bare-expression demonstrations use the displayed evaluation time. If the required reference is absent, report an unavailable prediction rather than choose an invisible anchor.

An unset object timezone is controller-local and unknown. `--assume-timezone=ZONE` fills only this gap and must be labeled as an assumption in every format. It cannot override an explicit object timezone. Bare expressions default to explicitly displayed UTC and accept `--tz ZONE`.

Failure to load a timezone locally means the plugin cannot calculate with it; it does not prove the controller rejected that timezone. A zero next-date result means the parser found no Occurrence within its search horizon, not a universal proof of impossibility. Preserve UTC offsets so repeated wall-clock times remain distinct.

## Overview and Summary

The standard Overview exposes recorded facts and explicit calculations: NAME, SCHEDULE, NEXT, LAST SCHEDULE, LAST SUCCESS, ACTIVE, SUSPEND, and a FINDINGS count. Show namespaces where needed to identify objects unambiguously. LAST SCHEDULE and LAST SUCCESS are the recorded status timestamps; their absence is not proof that no execution ever happened.

ACTIVE means the CronJob's recorded active Job references, not independently verified running Pods. A wide view can add configuration such as timezone, concurrency policy, deadline, history limits, and a schedule description without reading other resources. No default or wide run counts, duration statistics, failure streaks, or aggregate health verdicts are inferred.

The Summary covers the same selected CronJobs as the Overview. It counts total CronJobs, suspended CronJobs, those with active references, and timezone configuration. Support `--summary=show|only|hide`, with show as the default; Summary-only is a factual aggregate rather than a Findings-only mode.

Healthy CronJobs still produce Overview rows. An empty human Overview means no objects match the current selection or filtering; structured output remains a valid empty Report.

## Findings and Reports

Findings use stable descriptive kebab-case rule IDs and messages, with no severity ranking or prescribed fix. Initial rules cover configuration and calculation issues that can be established from CronJob data and local schedule evaluation. Clearly distinguish syntax errors, unavailable timezone calculations, explicit assumptions, and no Occurrence found within the parser's horizon.

Do not infer historical skipped-slot totals, failure streaks, deleted runs, replacement causes, or suspension duration. Retained Events and Jobs are not collected in v0.1.

`--problems` retains rows with Findings. `--no-findings` suppresses Findings consistently in human and structured output. Reject their combined use.

JSON and YAML share the versioned Report model under `cron.kubectl.dev/v1alpha1`. Include the evaluation timestamp, unavailable-value reasons, and timezone provenance. Represent missing timestamps as null. Scripts depend on stable rule IDs and structured fields, rather than message wording or table layout.

Exit codes are 0 for completed inspection, 1 for argument/input/required API failures, and optionally 2 for Findings when `--exit-on-findings` is enabled. Operational errors take precedence. Invalid configuration that was successfully inspected is reported as data with Findings.

## Compatibility, verification, and release

Officially target the latest three Kubernetes minors, currently 1.35-1.37. Use optional-field detection and permit older compatible `batch/v1` servers on a best-effort basis without a hard version gate. Document what was actually tested.

Verify schedule calculations with an injectable clock and fixtures covering timezone uncertainty, DST gaps and overlaps, descriptors, relative schedules, invalid inputs, and unavailable next dates. Exercise collection, analysis, and rendering through saved API fixtures and meaningful golden cases without requiring a live cluster in CI. Verify offline commands with unusable cluster configuration to ensure they stay offline.

Use the repository-local demo for human inspection. Inputs rejected by modern API admission belong in offline fixtures rather than a demo target that pretends they can be created on a normal cluster. Prepare GoReleaser, Krew metadata, and CI; publishing a release or submitting to Krew is a separate action.
